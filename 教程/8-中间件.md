# OpenViking 使用的中间件及能力

> 日期：2026-10-02；源码基线：`df32bf6e50a40843438f9491a26069ca4bd08f1f`。依据实际注册、包装与后端工厂；技术版本和模块职责分别见 [2-技术栈.md](2-技术栈.md) 与 [1-模块关系.md](1-模块关系.md)。

## 1. “中间件”的两类含义

本项目既有**代码中间件**（拦截 HTTP、队列生命周期、爬虫请求、Agent 上下文），也有**基础设施组件**（持久 KV、队列、缓存、对象存储、向量数据库、代理和监控）。二者分别列出：代码中间件通常在应用内运行，外部存储/代理服务是否启动取决于配置。

## 2. 主服务 HTTP 中间件

由 [server/app.py](../openviking/server/app.py) 的 `create_app` 组装。

| 中间件 | 使用的能力 | 触发/输入 | 输出或副作用 | 源码 |
| --- | --- | --- | --- | --- |
| CORSMiddleware | Origin/预检处理、允许方法/头、credentials、暴露响应头 | server.cors_origins；注册允许所有 method/header，暴露 X-Request-ID | 浏览器跨源访问所需 CORS 响应；OPTIONS 预检可能由该层直接处理 | [app.py](../openviking/server/app.py) |
| RequestIdMiddleware | 校验/替换请求 ID、上下文绑定、响应头、完成日志 | X-Request-ID：单值 ASCII、允许字符/长度；无效则生成 UUID | request.state.request_id、X-Request-ID、关联完成日志；不记录原始非法值 | [request_id.py](../openviking/server/request_id.py) |
| 显式 ExceptionMiddleware | 包住业务链中的异常并调用通用映射 | 存储/业务/未知异常 | 统一 status/error 信封；使 ID/CORS 外层仍能附响应头 | [app.py](../openviking/server/app.py)、[error_mapping.py](../openviking/server/error_mapping.py) |
| RequestTimingMiddleware | 计时、响应 header 注入、header 名称诊断 | HTTP 请求和 response.start | `X-Process-Time`；debug 日志只列 header 名称；耗时为生成 response.start 前的时间 | [timing_middleware.py](../openviking/server/timing_middleware.py) |
| ProfileMiddleware | cProfile 采样/汇总、路径脱敏、JSON 响应附加 profile | server.profile_enabled 且请求 profile 参数为真值 | 对适用的定长普通 JSON 对象加 profile，并重算长度；流式/下载/HEAD 不做此种改写 | [profile_middleware.py](../openviking/server/profile_middleware.py) |
| HTTPObservabilityMiddleware | HTTP 根 span、inflight、request lifecycle、错误上下文、身份与路由关联 | 请求/响应、trace carrier、最终路由模板与请求身份 | HTTP 事件→metrics/Usage Audit，OTel trace；忽略 health/ready/metrics 等高频探针 | [http_observability_middleware.py](../openviking/observability/http_observability_middleware.py) |
| 可选 dump_http_body | 读取/记录文本 body、截断 span 字符串、重建非流式响应 | server.observability.dump_body.enabled、max_bytes | request/response body 与体积属性；跳过指定流式/二进制内容类型 | [body_dump_middleware.py](../openviking/server/body_dump_middleware.py) |

### 2.1 包装顺序

Starlette 后注册的用户 middleware 在外层。下图是源码显式注册层的请求进入顺序，不展开 FastAPI/Starlette 自身的最外/最内框架处理层：

```text
CORS
 → Request ID
 → 显式 ExceptionMiddleware
 → Timing
 → Profile
 → HTTP Observability
 → 可选 Body Dump
 → 路由与依赖 / 挂载的子应用
```

响应按相反方向经过这些层。body dump 先注册，才位于 observability span 内；异常响应位于 ID/CORS 层内，才能复用响应头处理。profile/timing/observability 的原生 ASGI 实现维护流响应的执行路径，不能把它们都当成缓冲整个响应的同一实现。

### 2.2 能力边界与使用注意

- CORS 是浏览器访问策略，不能替代 API Key/ACL。允许源和 credentials 需与实际部署/前端连接方式匹配。
- body dump 的 max_bytes 限制**写入 span 的内容**；当前文本响应捕获仍可能读取全部 chunks 后重建，不能据此认定读取内存也严格限制在 max_bytes。开启后内容可能进入 trace，适合明确受控的调试。
- profile 是响应生成阶段的性能诊断，不等于数据库查询分析或所有异步后台任务的全程 profile。
- HTTP 根 span、返回 telemetry、metrics 和审计投影有不同生命周期，是否导出由 observability 配置控制。
- 业务异常、Pydantic RequestValidationError、框架 HTTPException 还有专用 exception handler；exception handler 与独立中间件是相关但不同的机制。

## 3. 鉴权与 MCP 边界

REST 通常使用 `Depends(get_request_context)`，由 auth registry 选择 dev/api_key/trusted/LDAP/OIDC plugin，再构造 RequestContext。鉴权并非所有 REST 请求都经过一个名为 AuthenticationMiddleware 的全局层。

MCP 则在自身 ASGI 应用外包装 `_IdentityASGIMiddleware`：

```text
主 FastAPI 中间件
 → /mcp 子应用身份层
 → 与 REST 共用 resolve_identity
 → contextvars 中绑定 RequestContext / 请求公网 URL
 → FastMCP 工具
 → service / VikingFS / vector 后端
```

该层解析 API Key/Bearer/账户/用户/actor-peer，失败返回 JSON-RPC 错误和 HTTP 401/403/400；OAuth 启用时可通过 WWW-Authenticate 指示 protected-resource 元数据；finally 恢复上下文，避免请求身份泄漏。实际工具数量以注册为准，旧 app 注释中的数量不作为清单依据。源码：[mcp_endpoint.py](../openviking/server/mcp_endpoint.py)、[auth](../openviking/server/auth/__init__.py)。

## 4. QueueFS 生命周期中间件

### 4.1 QueueMiddleware 契约

[queue_middleware.py](../openviking/storage/queuefs/queue_middleware.py) 定义 enqueue/process/ack/clear 四个方法与 invocation-local context，使用 `call_next` 形成链。

| 扩展点 | 能力 | 关键约束 |
| --- | --- | --- |
| enqueue | 在消息持久化前准备归属、持久化后登记 | committed 由 transport 设置；未提交才可补偿 |
| process | 消费前检查取消/归属，包住处理器 | 返回 ProcessResult；取消需等待 handler unwinding 后 settle |
| ack | 工作结束前后的索引维护 | ACK 提交失败回滚预准备状态，不能把已提交工作反向补偿 |
| clear | 批量工作快照与索引清理 | 快照不保证与并发 enqueue 隔离 |

构造传入的第一个 middleware 在最外层；队列拷贝为 tuple，不能运行时任意增删。实例可能被不同队列线程共享，不把单条消息状态保存在实例字段。

### 4.2 TaskWorkQueueMiddleware

[task_queue_middleware.py](../openviking/service/task_queue_middleware.py) 将 task ownership、取消、处理耗时、failure、活跃 coroutine 与 TaskWorkIndex 连接。入队登记、处理绑定 task context、ACK/clear 准备与失败补偿使 TaskTracker 能等待子工作。

**持久工作的事实来源仍是 QueueFS。** TaskWorkIndex 可以从工作消息重建，middleware 没有另建第二份持久消息数据库。QueueFS 的 pending→processing→ACK 与恢复带来至少一次交付，需要业务幂等性；它不是 exactly-once 保证。

## 5. 爬虫、模型网络与 Agent 中间件

| 场景 | 组件 | 使用的能力 | 边界 / 依据 |
| --- | --- | --- | --- |
| 递归网页获取 | Scrapy RequestValidatorMiddleware | 每个 outbound URL（含 redirects/retries）在发送前运行 request_validator，失败转 IgnoreRequest | 由 crawler settings 注册 priority=50；[middlewares.py](../openviking/parse/accessors/web_crawler/middlewares.py)、[web_crawler.py](../openviking/parse/accessors/web_crawler/web_crawler.py) |
| 爬虫框架默认链 | Scrapy retry/robots/redirect 等 | retry_times、DOWNLOAD_TIMEOUT/DELAY、并发/深度、ROBOTSTXT_OBEY | 当前 settings 显式配置对应功能；不是全套浏览器自动化或前端中间件 |
| HTTP 出网校验 | network_guard 和 HTTPX request hooks | DNS/IP、公网目标、允许列表、逐次请求/重定向限制 | 这是请求 hook/guard，非主服务 ASGI 层；[network_guard.py](../openviking/utils/network_guard.py) |
| 模型网络扩展 | ModelNetworkAdapter | 为扩展 URL scheme 注入 HTTPX/Requests transport | 只配置扩展端点时调用注册 adapter；[network.py](../openviking/models/network.py) |
| LangChain Agent | OpenVikingContextMiddleware | 在 Agent 执行前获取/注入 OV 上下文，处理策略与取消等生命周期 | 独立集成包的 AgentMiddleware，非主 REST 必需；[middleware.py](../examples/langchain/src/langchain_openviking/middleware.py) |
| 独立 VectorDB 服务 | FastAPI HTTP middleware | 向量 service 自己的请求统计/日志封装 | 独立 [server_fastapi.py](../openviking/storage/vectordb/service/server_fastapi.py)，不与主 app 注册列表合计 |

Bot hooks、React Axios interceptor 和模型 failover 也属于横切包装/适配，但并非同一种 middleware API。它们分别拦截宿主事件、客户端请求和模型调用。

## 6. 基础设施中间件：持久化、缓存、消息与检索

| 组件 | 用到的具体能力 | 接入点 | 默认/可选与范围 |

### 6.1 文件系统包装层

RAGFS 的顶层实际是 `Stats → PathLock → MountableFS`，挂载 backend 内再组合 encryption/cache/multiwrite。使用统计、exact/tree 锁、borrow/handoff、加密 envelope、缓存失效和跨 backend 路由能力。不能把这些“层”都理解成外部部署的中间件服务。

依据：[builder.rs](../crates/ragfs/src/core/builder.rs)、[mountable.rs](../crates/ragfs/src/core/mountable.rs)、[QueueFS](../crates/ragfs/src/plugins/queuefs/backend.rs)、[PersistStore](../src/store/persist_store.cpp)、[backend 工厂](../openviking/storage/vectordb_adapters/factory.py)。

## 8. 能力分类与校核结论

主 HTTP middleware、MCP 身份层、Queue middleware 和 Scrapy/Agent 扩展分别属于不同控制链。数据库、Redis、对象存储、向量后端、代理和监控也不能混为一套统一必装组件。

当前生产工作队列由项目自建 QueueFS 负责，观测 EventBus 是进程内旁路发布订阅；不能仅凭“异步/事件”就推断采用某个外部消息总线或通用任务框架。实际 SQLFS 已实现 SQLite，MySQL/TiDB 分支尚未实现；Cargo 的 optional sqlx 不作为已落地能力列入。
